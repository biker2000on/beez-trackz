# Atlas visit capture and confirmation contract

Implemented for the baseline inventory schema and mirrored in the retained legacy migration profile. Inventory quantities remain exclusively in inventory operations/movements and their projections. No generic visit workflow or balance table was introduced.

## Audio capture

`POST /api/v1/transcriptions` is multipart with `audio`, `ownerType` (`hive` or `apiary`), `ownerId`, and `mode` (`single`, `batch`, `apiary`). The browser supplies a stable UUID `captureId`, `observedAt` in RFC3339, and an IANA `timeZone`. `single` belongs to a hive; `batch` and `apiary` belong to an apiary. Legacy omitted capture identities are generated by the server.

The actor/capture pair is unique. An advisory lock serializes simultaneous uploads before storage. The server binds its SHA-256 audio hash, scope, mode, timestamp, timezone, and optional `replacesMediaFileId` to this identity. Exact replay returns the same `{mediaFileId}`. Conflicting reuse returns 409. A replay after an enqueue failure can enqueue the existing capture again using the existing stable job identity. A completed capture is not retranscribed on upload replay.

Completed audio must be committed to browser storage before upload; multipart requests do not enter the ordinary JSON offline queue. The server preserves audio and transcript versions under the existing retention/deletion policy.

The visit screen also exposes **Upload recording** without requesting microphone permission. A selected phone recording is saved locally with its filename, and its observation time can be checked before **Upload & review**. Reloading or reconnecting does not submit an unreviewed file automatically. M4A/MP4, MP3, WAV, OGG/Opus, WebM, FLAC and AAC recordings are accepted up to 64 MiB. The API identifies the actual container from bytes and stores the matching extension/content type; the transcription worker uses that detected type, including for older files incorrectly stored with a WebM suffix. This adds no database fields.

An optional `replacesMediaFileId` must belong to the same owner. Related replacement captures retain their source links. Confirmation locks the common original recording and checks the replacement family so two replacement accounts cannot both create a visit. A previously saved account must be corrected using record/reparse editing instead of confirming replacement audio as another visit.

## Read and review

`GET /api/v1/transcriptions/{id}` returns existing metadata plus `captureId`, persisted `mode`, `observedAt`, `timeZone`, `replacesMediaFileId`, and `outcomes` (the durable saved item receipts). Omitted query mode uses stored mode. A different mode cannot silently reinterpret the same capture.

The parsed inspection array adds `itemKey` and `scope: hive|apiary`. A version's first structured parse is cached on that transcript version; later reads preserve its item keys. Apiary items are notes observations and never receive a hive match. Hive candidates are restricted to the capture's owner hive or apiary. Missing queen observations remain null/omitted; they do not become false.

Equipment speech yields `equipmentActions: [{kind: deploy|return, referenceId: "", quantity, accepted: false, description}]`. The model cannot accept an action or select an actual inventory identity. The operator selects the equipment and checks acceptance. Existing feeding, treatment, queen, and mite fields remain supported.

## Confirm reviewed items

`POST /api/v1/transcriptions/{id}/confirm` accepts:

```json
{
  "mode": "batch",
  "versionId": "reviewed-transcript-version-uuid",
  "inspections": [{
    "itemKey": "item-0",
    "scope": "hive",
    "hiveId": "hive-in-this-apiary-uuid",
    "observedAt": "2026-09-11T13:15:00Z",
    "queenSeen": null,
    "notes": "Reviewed observations",
    "equipmentActions": [{
      "kind": "deploy",
      "referenceId": "inventory-item-or-equipment-type-uuid",
      "quantity": 1,
      "accepted": true
    }]
  }]
}
```

For new captures, `versionId` and a source item key/scope from the parsed review are required. The single hive is defaulted from a hive-owned capture. Apiary observations use `scope: apiary`, notes, and no hive. Apiary items cannot execute hive events/equipment actions. Observation time defaults to capture time. Future times more than five minutes ahead are rejected.

`X-Offline-Mutation-ID` can identify a single item command; the item body can also carry `mutationId`. If both exist they must agree. This identity is actor-scoped and bound to the source version and normalized payload. The source item key also protects replay independently of the header. Whole-request target validation rejects mixed-yard payloads before any write, including when the actor can edit both yards.

Each item commits independently. Within an item, the inspection, feeding/treatment/queen/mite records, accepted inventory commands, and receipt share one unit of work. Any failed action rolls the entire item back. `deploy.referenceId` identifies an inventory item or equipment type and uses home storage. Optional `sourceLocationId` must equal home; stock elsewhere must first be transferred home. `return.referenceId` identifies an existing deployment operation on that same hive. Both call the existing equipment service, including scoped edit authorization and reservation-aware stock checks. Editors receive no catalog/count/adjustment privilege through this endpoint.

The response is HTTP 200 for processed item outcomes, including partial failure:

```json
{
  "success": false,
  "inspectionIds": ["saved-inspection-uuid"],
  "apiaryInspectionIds": [],
  "feedingIds": [],
  "treatmentEventIds": [],
  "queenEventIds": [],
  "miteCountIds": [],
  "operationIds": [],
  "outcomes": [
    {"itemKey": "item-0", "status": "saved", "inspectionIds": ["saved-inspection-uuid"], "operationIds": []},
    {"itemKey": "item-1", "status": "failed", "error": "Review this item's stock action"}
  ]
}
```

Only a `saved` outcome is a receipt. Exact concurrent/repeated confirmation returns the same IDs; a changed payload for an already saved key returns a failed outcome and does not overwrite. Saved receipts remain readable on the capture after reload. The UI must inspect `success`/`outcomes`, retain unsuccessful drafts, and never treat HTTP 200 alone as a saved visit. Existing legacy recordings use stable per-target keys and cannot silently insert another walkthrough after older confirmed rows.

## Manual visits and failed transcription recovery

`POST /api/v1/inspection-visits` accepts `{captureId, scope, hiveId?, apiaryId?, observedAt, timeZone?, inspection}`. `inspection` uses the same fields and accepted equipment actions as confirmation. If `X-Offline-Mutation-ID` is supplied it must equal `captureId`. The same domain helper saves observations/events/equipment atomically, using null media/version references. The existing offline receipt runner persists the response in that transaction and returns exact replay. This endpoint is included in the generated JSON offline route manifest. It returns the same success/ID-array/outcomes shape with HTTP 201.

For captured audio whose transcription or parsing failed, confirmation accepts `manualEntry: true` and exactly one `itemKey: "manual-{captureId}"`. Existing source transcript versions are retained. If no current version exists, a version explicitly labeled provider `manual-entry` stores the typed account; original audio and transcription failure status remain intact. The confirmed inspection still references the actual media. Manual recovery cannot add a second visit after other items were saved.

`POST /api/v1/apiary-inspections` remains a simple notes-only command accepting `{apiaryId, observedAt, notes, captureId? | mutationId?}`. `GET /api/v1/apiary-inspections?apiaryId=...` returns the latest 200 observations newest first. Both enforce apiary access. The atomic visit endpoint is preferred when shared offline receipt behavior is needed.

## Verification

Database-backed regression tests cover simultaneous confirmations and exact receipt replay, changed replay rejection, stale source versions, an editor of two apiaries attempting a cross-yard batch, partial outcomes, rollback of an inspection when accepted equipment cannot deploy, original observation time on feeding/inventory events, nullable queen observations, manual receipt replay without fabricated media, and failed-transcription manual source retention. Baseline tests exercise real inventory deployment and shortage rollback; legacy-profile tests exercise the mirrored additive migration. Parser tests ensure model-supplied equipment IDs/acceptance cannot become accepted commands and yard observations remain separate from hive observations.
